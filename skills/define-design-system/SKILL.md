# 디자인 시스템 정의

실제 프로젝트의 근거로 디자인 결정을 만들고 `문제 → 과업 → 원칙 → 명세 → 검증`을 연결한다. 사용자와 대화하며 현재 단계의 문서를 작성한다. 사용자가 요청한 단계 또는 수행 가능한 범위까지 진행하며, 설명이나 빈 템플릿 생성만으로 끝내지 않는다.

## 시작과 재개

1. 프로젝트 지침, 기존 디자인 문서·구현·연결된 자료를 필요한 범위에서 읽는다. 이 스킬을 만드는 저장소와 적용 대상 프로젝트를 혼동하지 않는다.
2. [진행 프로토콜](references/workflow.md)을 읽는다. 기존 진행 기록이 있으면 근거와 변경 사항을 확인하고 재개한다.
3. 적용 프로젝트·목적·범위가 자료로 확인되지 않으면 핵심 질문 1~3개만 먼저 묻는다. 이미 답한 내용을 다시 묻지 않는다.
4. 신규 서비스는 [신규 프로젝트](references/conditions/new-project.md), 기존 서비스는 [기존 프로젝트](references/conditions/existing-project.md)를 읽는다. 미확정이면 확인된 내용으로 초안을 만들고 해당 분기를 확정하지 않는다.
5. 사용자 조사·접근 권한·구현 환경이 부족하면 [근거 부족](references/conditions/limited-evidence.md)을 적용한다. TDS/KRDS 자산·규칙을 채택하거나 플랫폼 제약을 정할 때는 [적용 환경](references/conditions/platform-and-reference.md)을 읽는다.
6. 아래에서 현재 단계 하나와 연결된 템플릿만 읽는다. 전체 참조 파일을 한꺼번에 로드하지 않는다.

## 수행 원칙

- 매 단계에서 자료를 먼저 확인하고, 미해결 질문을 묻고, 확인 가능한 부분을 작성하고, 게이트를 평가한 후 진행 기록을 갱신한다. 단계마다 형식적인 승인 요청을 반복하지 않는다.
- 방법론은 의사결정에 필요한 만큼 적용한다. [근거 자료](references/sources.md)의 공식 내용과 이 스킬의 권장 절차를 구분한다. TDS/KRDS의 색·치수·모든 구성요소를 무조건 이식하지 않는다.
- 이 스킬의 기본 작업은 정의 문서 작성이다. 실제 구현·배포·Figma 라이브러리 게시 등은 사용자가 요청한 범위에 포함될 때만 수행한다. 외부 메시지를 보내지 않는다.
- 사용자가 지정하지 않으면 적용 프로젝트의 `docs/design-system/`을 산출물 위치로 제안하고, 충돌 없는 경로라면 작성한다. 기존 파일을 통째로 덮어쓰거나 스킬의 템플릿 자체를 프로젝트 결과로 수정하지 않는다.
- 템플릿의 `{{...}}`는 작성 지시용 자리다. 실제 산출물에는 확인된 값, `미확정`, `해당 없음: 이유` 중 하나로 바꾼다. 실제 검증을 하지 않은 칸은 `미수행`으로 기록한다.
- 종료 시 작성 파일, 결정 사항, 현재 단계, 게이트 결과, 남은 질문과 다음 행동을 보고한다. 정의 초안과 실제 검증 완료를 구분한다.
