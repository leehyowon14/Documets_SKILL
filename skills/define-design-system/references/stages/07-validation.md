# 07 실제 흐름 검증

입력: 평가 대상 버전, 대표 흐름, 명세·수용 기준, 지원 환경. 실행이 불가능하면 [근거 부족](../conditions/limited-evidence.md)을 적용한다.

## 질문

- 어떤 사용자·제작자·환경을 대표해야 하는가?
- 과업 완료와 심각한 실패를 어떻게 판단할 것인가?
- 실제 사용자 평가와 구현 샘플을 사용할 수 있는가?
- 기존 사용처 중 회귀 위험이 큰 곳은 어디인가?

## 방법론 실행

1. 먼저 대상 버전·과업·환경·평가 방법·성공 조건을 고정한다. 결과를 본 뒤 통과 기준을 낮추지 않는다.
2. 서비스 사용자는 해결 방법을 알려주지 않는 과업으로 관찰한다. 완료, 도움 필요, 오해, 오류 복구, 결과 이해를 기록한다. 참여자 구성을 기록하며 소수 관찰을 전체 성공률로 일반화하지 않는다.
3. 제작자 파일럿에서는 작성에 참여하지 않은 사람이 문서로 다른 대표 화면을 만들게 한다. 탐색 실패·이해 불가·임의 override·추가 질문을 기록한다. 혼자 수행한 경우 자체 점검으로 표시한다.
4. 선언한 환경에서 자동 검사와 수동 접근성·상호작용 평가를 결합한다. 실제 증거 경로와 수행자를 기록한다.
5. 경계 사례를 명세에서 가져온다. 기본 검토 후보: 0건/긴 콘텐츠, 느린 응답/명시적 실패/결과 미확정, 연속 입력, 취소·재개, 키보드·포커스, 확대·다국어·테마. 관련 없는 항목은 이유와 함께 제외한다.
6. 결함을 과업 차단·데이터 손실 가능성·복구 가능성·접근성 영향으로 분류한다. [실패·변경](../conditions/revision-and-resume.md)에 따라 관련 단계만 수정·재검증한다.

## 산출물

[검증 계획·결과 템플릿](../../assets/templates/07-validation.md) → `07-validation.md`. 원시 로그·캡처·보고서는 접근 가능한 실제 경로로 연결한다. 불필요한 개인정보를 문서에 복제하지 않는다.

## 필수 게이트

- G07-1: 대상 버전·흐름·환경·평가 방법이 명시되고 실행 결과와 근거가 존재함.
- G07-2: 선언한 핵심 과업에서 차단 결함과 중대한 접근성 결함이 해결되고 재검증됨.
- G07-3: 서비스 사용자 평가와 제작자 파일럿의 관찰 결과가 있음. 미수행·자체 점검만 있으면 이 항목은 미확인.
- G07-4: 실제 평가와 계획이 분리되고, 미검증 범위·남은 위험·후속 책임이 기록됨.

자동 테스트 통과·시안 생성·컴포넌트 데모만으로 이 단계를 passed로 처리하지 않는다. 대상이 코드 없는 정의 문서뿐이면 검증 계획을 전달하고 07은 in-progress/deferred/blocked 중 실제 상황에 맞게 기록한다.
