# 08 운영·배포 정의

입력: 확정/잠정 명세, 검증·결함 기록, 팀의 실제 운영 방식. 이 단계의 문서 작성은 07이 진행 중이어도 가능하지만 검증 완료나 배포 완료를 의미하지 않는다.

## 질문

- 제안·검토·유지보수의 책임자는 누구인가? 혼자 운영할 경우 어떤 점검 기록을 남길 것인가?
- 어떤 변경을 공통 시스템에 채택하고 어떤 변경을 제품에 남길 것인가?
- 토큰·디자인·코드·문서 버전은 어떻게 맞추는가?
- 호환성이 깨질 때 이전·폐기·되돌리기는 어떻게 하는가?
- 예외는 누가 언제 재검토하며 효과는 무엇으로 측정하는가?

## 방법론 실행

1. 작은 문구 수정과 다수 사용처에 영향을 주는 API·토큰 변경을 구분한다. 영향이 큰 변경에 RFC를 적용하고 일상 수정에 불필요한 승인 절차를 추가하지 않는다.
2. 공통화 제안은 유용성, 중복 여부, 사용성, 기존 체계와의 일관성, 여러 환경 적합성으로 검토한다. 팀 규모에 맞는 담당자를 지정한다.
3. 제안→실험→검증→안정→폐기 예정→제거의 전환 조건을 정한다. 실험 상태의 사용 제한과 종료 조건을 적는다.
4. 기준 원본·배포 대상·버전 대응·호환 별칭·이전 방법·되돌리기 범위를 정한다. 정의 요청만으로 패키지 게시나 서비스 배포를 수행하지 않는다.
5. 적용 가능 요소를 분모로 한 채택률, 동등한 과업의 제작 시간, 예외와 결함을 측정한다. 채택률을 올리기 위해 타당한 제품 예외를 제거하지 않는다.

## 필수 게이트

- G08-1: 제안·결정·유지보수 책임과 처리 경로가 확인됨.
- G08-2: 기준 원본·버전·배포·호환·이전·폐기 규칙이 적용 환경에 맞게 정의됨.
- G08-3: 예외의 이유·범위·재검토 계기와 측정 계획이 존재함.
- G08-4: 현재 완료 수준이 실제 단계 상태와 일치하고 미검증·미배포를 숨기지 않음.

종료 시 `status.md`의 전체 게이트와 산출물 경로를 확인한다. 더 이상 구현 작업이 요청되지 않았다면 운영 문서를 넘기고 정의 작업을 종료한다.
