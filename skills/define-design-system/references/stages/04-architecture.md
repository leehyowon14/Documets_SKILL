# 04 시스템 구조와 책임

입력: 과업·원칙·기존 인벤토리. Atomic Design을 요소와 실제 화면을 왕복하는 도구로 사용한다. atoms/molecules 등의 폴더명을 강제하지 않는다.

## 질문

- 여러 제품에서 의미와 동작이 같은 요소는 무엇인가?
- 제품별 정책이나 데이터 형태 때문에 동작이 달라지는 요소는 무엇인가?
- 현재 이름·속성·Figma와 코드의 대응에서 혼란은 어디에 있는가?
- 기존 사용처를 보존해야 하는가? 교체한다면 어떤 단위로 이전할 수 있는가?

## 방법론 실행

1. 대표 화면을 파운데이션·토큰·컴포넌트·패턴·서비스 흐름으로 분해한다. KRDS의 패턴 분류와 Atomic Design을 기계적으로 일대일 매핑하지 않는다.
2. 후보마다 목적·동작·상태가 같은지 비교한다. 단순한 외형 유사성만으로 합치지 않는다.
3. 공통/도메인 경계를 정한다. 예: 버튼은 공통, 취소 수수료 계산은 제품 정책. 서버 중복 방지는 제품 계약이며 UI 규칙으로 대신할 수 없다.
4. 차이를 제한된 속성이나 조합으로 표현할 수 있는지 확인한다. 사용처마다 조건문·불리언 조합이 늘면 분리를 검토한다.
5. Figma 이름·코드 이름·속성 대응을 정하고 기존 항목에는 유지/통합/대체/도메인 잔류 결정을 남긴다.

- G04-2: 대표 화면을 분해한 뒤 다시 조합할 수 있으며 핵심 과업 요소가 누락되지 않음.
