# 01 목적·범위

입력: 제품 요구, 사용자·제작자의 실제 작업 사례, 기존 화면·코드·브랜드 자료. 먼저 신규/기존 조건 파일을 적용한다.

## 질문

- 누구의 어떤 문제가 이번 작업의 계기인가? 서비스 사용자와 제작자 문제를 각각 확인한다.
- 최근 문제가 발생한 화면·작업·상황을 보여줄 수 있는가? 해결에 든 재작업은 무엇인가?
- 적용할 제품·플랫폼과 반드시 유지할 기존 계약은 무엇인가?
- 이번에는 정의 문서, 파일럿 구현, 배포 중 어디까지 필요한가?
- 디자인·개발 판단을 맡을 사람과 사용할 수 있는 자료·시간은 무엇인가?

## 방법론 실행

1. 이해관계자 인터뷰에서는 추상적인 선호보다 최근 실제 사례와 자료를 요청한다. 이미 있는 기록은 출처와 함께 재사용한다.
2. UI Audit 표본을 과업·역할·기기·정상/실패 상태로 나눈다. 같은 역할끼리 캡처·코드 위치·이름·변형·행동을 비교한다.
3. 각 항목을 관찰, 사용자 결정, 해석, 미검증 가정으로 구분한다. 빈도가 높은 UI도 사용성 근거 없이 표준으로 선정하지 않는다.
4. 반복 구현·일관성·사용자 오류 중 해결할 문제를 정하고 제외 범위를 기록한다.
5. 성공 지표의 측정 단위·대상·기간을 정의한다. 기준선이 없으면 측정 계획으로 남긴다.

## 필수 게이트

- G01-1: 대상 사용자·제작자, 제품·플랫폼, 요청 범위와 제외 범위가 명시됨.
- G01-2: 핵심 문제에 근거 또는 HYP와 확인 계획이 연결됨. 조사 표본·미조사 범위가 구분됨.
- G01-3: 지표에 분모·측정 방식 또는 기준선 수집 계획이 있고 허위 개선 수치가 없음.
- G01-4: 필수 제약과 결정 담당자가 확인됨. 담당자 미정이면 운영 확정에 대한 의존성을 기록하고 해당 게이트는 미확인.

통과는 조사 자체의 완벽함을 의미하지 않는다. 가설을 포함할 수 있지만 범위 결정을 바꿀 중대한 미결 질문은 해결하거나 범위에서 명시적으로 분리해야 한다.
