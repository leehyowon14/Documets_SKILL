# 06 컴포넌트·패턴 계약

입력: 구조·토큰·대표 과업. Contract-first, 상태 전이 모델, Example Mapping을 결합한다.

## 질문

- 언제 이 요소를 쓰며 다른 요소가 필요한 경우는 언제인가?
- 필수/선택 영역과 허용되는 변형은 무엇인가?
- 입력·대기·완료·실패·취소에서 사용자에게 무엇을 알려야 하는가?
- 키보드·포커스·보조 기술 처리는 요소와 사용처 중 누가 책임지는가?
- 데이터 보존·재시도·중복 요청·결과 미확정 처리는 어느 계층의 책임인가?

## 방법론 실행

1. 각 컴포넌트의 목적·구조·props·이벤트·상태·접근성·레이아웃 계약을 구현 전에 작성한다. 실제 기술 스택이 미정이면 의미 계약과 구현 매핑을 분리한다.
2. 상태 전이표에 현재 상태, 사건, 조건, 다음 상태, 시각/음성 안내, 부수 효과를 적는다. 변형은 외형 선택이고 상태는 동작 상황임을 구분한다.
3. Example Mapping으로 규칙마다 정상·경계·예외 사례와 미결 질문을 연결한다. 사례가 없는 복잡한 규칙은 범위를 좁힌다.
4. 단일 요소로 해결되지 않는 입력 검증·제출·검색·복구를 패턴 계약으로 작성한다. 사용자 목적·서버 책임·표현 책임을 분리한다.
5. 기본값, 허용/금지 조합, 긴 텍스트, 콘텐츠 없음, disabled/read-only/loading 차이, 포커스 이동·복귀, 결과 미확정 등을 해당 요소에 맞게 검토한다.
6. 사용자 요청에 구현이 포함되면 작은 대표 샘플을 만들고 07로 연결한다. 문서 요청만 있으면 실행 가능한 검증 시나리오까지 작성한다.

## 필수 게이트

- G06-1: 선택한 과업의 컴포넌트·패턴마다 목적·사용/비사용 조건·계약이 있음.
- G06-2: 관련 상태·전이·허용 조합·경계 사례가 정의되고 모순이 없음.
- G06-3: 접근성·입력 보존·재시도·서버 의존 책임이 명확함.
- G06-4: 핵심 미결 정책이 해결되며 실제로 실행할 수 있는 수용 기준이 있음.

명세 완성과 구현 검증은 별개다. 서버 타임아웃을 무조건 실패로 정의하거나 로딩 표시만으로 중복 생성 방지를 보장하지 않는다.
