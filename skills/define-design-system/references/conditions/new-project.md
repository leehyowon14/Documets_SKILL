# 조건: 신규 프로젝트

적용: 실제 서비스·사용 기록·공통 라이브러리가 아직 없거나 초기 프로토타입만 존재.

- 01의 UI Audit 대신 요구사항, 유사 과업의 실제 이용 경험, 기술·브랜드 제약을 조사한다. 경쟁 서비스 캡처를 자사 사용자 관찰로 취급하지 않는다.
- 02에서 핵심 과업과 예상 실패 상황을 가설로 만들고, 확인할 연구 질문을 지정한다. 사용자 인터뷰를 못 하면 [근거 부족](limited-evidence.md)을 따른다.
- 04에서 제품 차별화 영역과 반복될 가능성이 있는 공통 요소를 분리한다. 미래의 모든 서비스를 예상해 범용 API를 만들지 않는다.
- 05~06은 대표 흐름에서 필요한 최소 규칙으로 시작한다. 무작정 토큰·컴포넌트 수를 목표로 삼지 않는다.
- 07에서 첫 파일럿의 측정값을 기준선으로 남긴다. 기존 대비 개선 수치를 만들어내지 않는다.

추가 질문: 첫 출시의 핵심 사용자와 과업은 무엇인가? 사용할 수 있는 브랜드 자료·기술 스택은 무엇인가? 어떤 가설이 틀리면 첫 화면이나 구조가 바뀌는가?

산출물 보정: 인벤토리의 `현재 사용처` 대신 `계획된 사용처`를 쓰고 모든 예상은 HYP로 연결한다.
