# 조건: 플랫폼·참고 시스템 적용

## 먼저 정할 축

웹/네이티브/임베디드 환경, 입력 방식, 지원 화면 크기, 언어, 정보 밀도, 테마, 접근성 목표와 검사 범위. 기존 제품 계약과 사용자 요구를 기준으로 정하고 고정된 브레이크포인트·폰트·다크 모드를 임의로 필수화하지 않는다.

## TDS·KRDS 사용 방식

- **참고:** 구조·명세 작성법을 학습해 자체 결정으로 재구성. 출처를 적고 예시 숫자를 규정으로 승격하지 않는다.
- **일부 채택:** 채택 항목과 변경 항목을 표로 구분. 디자인·코드 자산을 실제 복제하려면 현재 사용 조건과 플랫폼 적합성을 확인한다.
- **직접 적용:** 지정 플랫폼·기관의 요구가 있으면 현재 공식 문서와 적용 버전을 확인한다. 이 스킬의 권장 절차가 해당 요구를 대체하지 않는다.

공공 서비스의 KRDS 적용 의무나 앱인토스의 TDS 사용 범위는 프로젝트별로 확인한다. 모든 제품에 동일하게 강제하지 않는다. 공식 설명의 "필수"를 자체 서비스 전체의 법적 의무로 해석하지 않는다.

TDS 공개 Mobile 문서로 확인하지 않은 내부·데스크톱 시스템의 동작을 추정하지 않는다. KRDS 고대비 모드와 일반적인 다크 모드를 같은 요구로 취급하지 않는다.

## 평가 방법 조정

- 웹: 의미 있는 요소, 포커스, 키보드, 스크린 리더, 확대·리플로와 선언한 접근성 목표를 검증.
- 네이티브: 해당 플랫폼의 접근성 API, 글자 크기 설정, 탐색·제스처·보조 기술을 검증.
- 입력이 복잡한 서비스: 표·필터·다국어·정보 밀도에서 실제 과업 수행 확인.
- 테마 지원: 배경/전경/상태 조합별 검증. 테마 이름만 존재하는 것으로 지원 완료 판단 금지.

현행 규격·라이선스·API 판단이 필요할 때 [출처](../sources.md)의 공식 원문을 확인하고 확인일·버전을 기록한다. 접근 실패 시 확인한 범위와 미확인을 분리한다.
