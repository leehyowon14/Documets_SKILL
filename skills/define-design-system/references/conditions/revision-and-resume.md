# 조건: 검증 실패·요구 변경·중단 후 재개

## 실패를 원인에 맞는 단계로 반환

| 발견 사항 | 우선 재검토 | 후속 영향 확인 |
|---|---|---|
| 사용자의 목표·과업 오해 | 01~02 | 03~07의 관련 결정 |
| 원칙의 해석 충돌 | 03 | 관련 컴포넌트·패턴 |
| 과도한 props·도메인 조건문 | 04 | 06 API·08 이전 규칙 |
| 대비·밀도·확대 시 가독성 문제 | 05 | 관련 06 요소·07 검사 |
| 실패 복구·포커스·상태 누락 | 06 | 관련 07 시나리오 |
| 제작자가 문서만으로 사용 불가 | 04/06/08 | 파일럿 재수행 |

1. 결함의 재현 조건, 영향, 근거, 해당 버전을 기록한다.
2. 영향을 받는 결정과 테스트를 추적한다. 관련 passed 단계를 stale로 바꾸고 기존 결과를 삭제하지 않는다.
3. 원인과 직접 연결된 수정안을 적용한다. 관계없는 전체 절차를 반복하지 않는다.
4. 새 버전에서 실패 시나리오와 영향받는 회귀 범위를 재검증한다. 미실행이면 미확인으로 남긴다.

사용자가 완성되지 않은 동작을 발견했다면 설명 문서나 상태만 바꿔 해결했다고 주장하지 않는다. 저장소의 커밋 처리 지침과 기존 사용자 권한 범위도 따른다.

## 재개

- `status.md`, 현재 단계 산출물, 미결 질문, 최근 결정부터 읽는다.
- 기록된 버전과 현재 코드·디자인·요구 변경을 비교한다. 범위가 큰 경우 변경 목록부터 확인한다.
- 유지 가능한 게이트는 재사용한다. 이전 검증과 다른 대상은 stale로 표시한다.
- 이전에 답변한 질문을 재질문하지 않는다. 답변의 전제가 달라졌을 때만 변경 이유를 설명하고 확인한다.
- 현재 단계, 변경된 전제, 바로 할 작업을 짧게 알리고 계속한다.

변경 영향과 이전 검증의 처리 예시는 [계약 변경 후 재개](../examples/resumed-contract.md)를 참고한다.
