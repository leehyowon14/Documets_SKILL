# 작성 예시: 계약 변경 후 재개

이 파일은 가상의 변경 요청과 기록 예시다. 실제 테스트 실행의 증거가 아니다.

## 가상 입력

> 이전 명세에서 이어서 해줘. 예약 요청이 타임아웃이어도 서버에서는 생성되는 경우가 있어. 실패 화면에서 바로 재시도하게 되어 있는데 이 부분부터 수정해줘. 코드는 아직 바꾸지 말고.

기존 기록: 명세 v0.1, PAT-01은 타임아웃→실패→재시도로 정의. 07에는 v0.1 기준 평가 결과가 존재한다고 가정한다. 서버의 결과 조회·중복 방지 지원 여부는 자료에 없다.

## 재개 시 행동

1. 기존 status, PAT-01, TEST-01, 실제 변경 요청을 확인한다. 검증 기록의 버전과 범위를 읽는다.
2. 06과 영향받는 07을 stale로 표시한다. 01~05는 영향 여부를 확인하고 타당한 기존 결정을 유지한다.
3. "결과 조회 또는 중복 방지 키를 서버에서 지원하나요?"를 묻는다. 이는 재시도 조건을 결정하는 필수 정보다.
4. 답변 없이 가능한 상태 명세를 수정한다. 조회 API가 있다고 가정하거나 새 API를 이미 구현한 것으로 쓰지 않는다.
5. 기존 평가 결과를 보존하고 v0.2의 재검증 계획을 추가한다. 코드는 변경하지 않는다.

## PAT-01 v0.2 잠정 수정

| 현재 상태 | 사건 | 다음 상태 | 안내·허용 행동 | 제품·서버 의존성 |
|---|---|---|---|---|
| 처리 중 | 응답 시간 초과 | 결과 미확정 | 확정 여부를 확인 중임을 설명, 무조건 재제출하지 않음 | 결과 조회 가능 여부 미확정 |
| 결과 미확정 | 생성됨을 서버에서 확인 | 완료 | 예약 결과 표시 | 조회 수단 필요 |
| 결과 미확정 | 미생성·안전한 재시도가 확인됨 | 재시도 가능 | 사용자에게 재시도 경로 제공 | 안전 조건의 서버 계약 필요 |

조회 수단이 없다면 고객 지원·별도 확인 등 제품이 제공할 수 있는 회복 경로를 담당자와 정한다. 영구적으로 대기 화면만 보이게 하는 것도 완료된 패턴으로 간주하지 않는다.

| 항목 | 판정 | 이유·다음 행동 |

전달 예시: "PAT-01에 결과 미확정 상태를 추가했습니다. 서버의 조회·재시도 계약은 미확정이라 명세는 잠정입니다. 이전 검증은 보존했고 새 버전은 재검증 대기 상태입니다. 코드는 변경하지 않았습니다."
